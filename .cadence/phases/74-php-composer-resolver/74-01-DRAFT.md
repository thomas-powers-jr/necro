# 74-01 — PHP composer-autoload resolver (namespace/class → file)

## Objective

Port the composer.json PSR-4/PSR-0/classmap/files autoload resolution plus per-file namespace/`use`-import resolution to PHP — mirroring Python's three-file module-resolver/import-parser/resolve-import shape (its own Phase B, `src/graph/python/{module-resolver,import-parser,resolve-import}.ts`) — per `.cadence/intelligence/php-support-design.md` §4 Phase B, using PHP grammar facts (`namespace_definition`, `namespace_use_declaration` in all its shapes, top-level declaration node types) verified live against `tree-sitter-php.wasm` this session, not assumed by analogy to Python's or JS's grammar. No user-visible change: this phase produces new `src/graph/php/*` resolver modules with no call sites in `src/engine/model.ts`/`scan()` yet — that wiring is Phase C.

## Acceptance Criteria

### AC-1: composer.json's four autoload strategies parse into a namespace/class → file map
Given a composer.json with `psr-4` (single prefix, multiple prefixes, array-of-dirs-per-prefix), `psr-0` (legacy underscore-as-directory-separator convention), `classmap` (directories and/or explicit file paths), and `files` (unconditionally-included scripts) entries, plus the `autoload-dev` block (needed so AC-4's real-repo harness recognizes a corpus repo's own test namespace — e.g. phpunit's own `Tests\` PSR-4 prefix — as a local, not external, reference)
When the autoload-map builder runs
Then: `psr-4`/`psr-0` entries resolve FQCN→file by pure path manipulation (no file content read) per each spec's own convention — PSR-4: prefix maps to a base dir, remaining namespace segments mirror subdirectories 1:1, case-sensitive; PSR-0: namespace separators **and** underscores in the class name both map to directory separators, per the legacy spec **for flat/legacy-style prefixes** (ending in `_`, e.g. `Zend_`) — folding every nested directory segment into one underscore-joined class name; `classmap` entries resolve by scanning candidate files under the given directories/paths and reading each file's actual `namespace_definition` + top-level declaration name to build the real FQCN, since classmap entries are "not namespace-derived" per design doc §1; `files` entries are collected as a separate unconditionally-included path list, not merged into the FQCN map (composer autoloads these by side effect, not by class name); a missing/malformed composer.json, or a present file with no `autoload`/`autoload-dev` block, returns an empty map — never throws (mirrors `module-resolver.ts`'s "best-effort default, not a throw"). **Correction made during implementation**: for namespace-style PSR-0 prefixes (ending in `\`, e.g. `Doctrine\`), underscore-folding is deliberately **not** attempted, even on the final segment — composer's forward algorithm converts every underscore in the class-name portion to a directory separator, so a discovered file literally named `Foo_Bar.php` can never have come from an underscored class name in the first place (it can only be a namespace segment named `Foo_Bar` verbatim, or a non-PSR-0-strict repo). Attempting the fold would produce a wrong, confidently-asserted map entry (`Vendor\Foo\Bar` for a class composer would only ever look up as `Vendor\Foo\Bar` with `Foo_Bar` as one literal segment) rather than correctly reporting unresolved. This is a genuine, inherent path→FQCN ambiguity (whether an intermediate or final directory segment originated from a real `\` or a folded `_` cannot be determined from the path alone), not a fixable gap — confirmed via advisor consult after a first-draft fix attempt was shown to be actively wrong, not just incomplete. PSR-0 is legacy and not exercised by either AC-4 corpus repo (guzzle, phpunit both use PSR-4 only).

### AC-2: Per-file `namespace`/`use` declarations parse into a local-binding map, covering every verified `use`-clause shape
Given a PHP file with a `namespace` declaration and `use` declarations in each shape verified live this session: simple qualified (`use Foo\Bar;` → `qualified_name` node wrapping a `namespace_name_as_prefix` + trailing `name`), single-segment (`use Foo;` → a **bare `name` node with no `qualified_name` wrapper** — a distinct grammar shape, easy to miss), aliased (`use Foo\Bar as Baz;` → a sibling `namespace_aliasing_clause`), grouped (`use Foo\Bar\{Baz, Qux};` → `namespace_use_group`/`namespace_use_group_clause`), and `function`/`const`-prefixed (`use function Foo\bar;` / `use const Foo\BAR;` → distinguished by an **unnamed** `"function"`/`"const"` token child of `namespace_use_declaration`, immediately after the `"use"` token — not a named field)
When the import parser walks the file
Then every `use` clause produces a `{ localName, fqcn, kind }` entry, `kind` distinguishing class/function/const so callers apply PHP's real autoload rule correctly — composer's `psr-4`/`psr-0`/`classmap` only autoload class-like symbols (classes/interfaces/traits/enums); function/const imports can only ever resolve via a `files`-autoload script, never via `psr-4`/`psr-0`/`classmap`, so the resolver must never silently mismap them against the class map — and the file's own current namespace (or the global namespace if no `namespace` declaration is present) is captured for AC-3. **Correction made during implementation**: "report unresolved unless found among `files` entries" (the original wording here) over-promised a `files`-list cross-check this phase never builds — doing so would require scanning `files`-listed scripts for top-level function/const declarations, a new piece of work (a function/const analog of T3's class-declaration extraction) with no design-doc mandate and no test coverage need for AC-4's corpus. What this phase actually delivers: `kind` is captured correctly and completely (verified against every use-clause shape, including group-level `function`/`const` prefixes) so a *future* caller can apply the distinction; T5/AC-3's resolver is explicitly class-kind-only, matching design doc §4 Phase B's "namespace/class → file" framing — function/const resolution is out of scope for this phase, full stop, not "attempted but unresolved."

### AC-3: Class-name references resolve to files using PHP's actual namespace-resolution rules, not JS's or Python's
Given AC-2's local-binding map and current-namespace context, plus a name appearing in class-reference position (a `use` import target, an `extends`/`implements` clause, `new X()`, or the class-name side of `X::method()`)
When the resolver classifies and resolves the reference
Then: a leading-backslash name (`\Foo\Bar`) is always fully qualified — resolved directly against the composer map regardless of current namespace or any `use` imports; otherwise, only the reference's *first* segment is ever checked against `use` imports' local names (class-kind only) — a match substitutes that import's FQCN for the first segment with any remaining segments appended, which covers both the single-segment case (`Foo` after `use App\Foo;` — the single most common real-world pattern, resolves via the import, not the current namespace) and the qualified-relative case (`Sub\Foo` after `use App\Sub;`) with one rule, since PHP's own algorithm treats them identically; if the first segment matches no import, the *whole* name is qualified by prepending the current namespace — PHP has **no** global-namespace fallback for class names, unlike its function/const fallback rule (a real, easy-to-invert asymmetry). All branches tested explicitly, including the import-match case for both single- and multi-segment names.

### AC-4: An import-resolution-rate harness measures the resolver against real PHP repos, mirroring Python's own Phase B "Done" bar
Given design doc §3/§4 Phase B's "Done" line (≥95% class/namespace references resolved on guzzle + phpunit checkouts, recorded number) and the shipped Python precedent (`src/bench/python-import-resolution-rate.ts`, phase 44-00 AC-7 — not vendored into the repo, not wired into CI, run manually)
When a `--repo <path>` harness walks every `.php` file's `use` imports and resolves each *local* class-kind candidate against the built autoload map
Then it reports resolved/total and the resulting rate for each of the two pinned local checkouts, recorded in PROGRESS/SUMMARY — not asserted from vibes, and not an enforced CI gate (Phase D owns the enforced precision/recall floor). **Correction made during implementation**: the locality/measurement rule went through three empirically-forced refinements, all against real guzzle/phpunit checkouts (not assumed up front) — (1) locality is a reference's *containing namespace* being populated by a real discovered class in the built map (not a bare top-level-segment check), since guzzlehttp/guzzle's own composer.json declares only `GuzzleHttp\` but its imports also reference sibling Composer packages (`GuzzleHttp\Psr7\*`, `GuzzleHttp\Promise\*`) sharing that namespace root by publisher convention — a first-segment check misclassified those as local failures and cratered guzzle's rate to 66.9%; (2) a bare namespace-alias import (`use GuzzleHttp\Psr7;`, valid PHP that imports a namespace as a local alias, never autoloaded by composer) is excluded when the FQCN is itself proven a namespace — either as a strict prefix of some *other* imported FQCN repo-wide, or by being independently populated in this repo's own map — which brought guzzle to 89.4%; (3) that exclusion is checked *only when the candidate doesn't already resolve* — `PHPUnit\Framework\TestCase` is simultaneously a real class and, legitimately, a namespace container for its own sibling helper classes (`PHPUnit\Framework\TestCase\ExceptionExpectation`), so applying the namespace-alias exclusion unconditionally wrongly dropped phpunit's `resolved` count; checking resolution first fixed it. Final measured numbers: guzzle 355/360 (98.6%), phpunit 7164/7263 (98.6%), both well above the 95% floor. Diagnosed-but-not-chased-further (both repos already clear the floor; not a resolver bug, a Phase C carry-forward — see SUMMARY): guzzle's `tests/Psr17SpyFactory.php` declares `SpyStream`/`SpyResponse` as extra classes alongside its filename-matching class, and phpunit's `PHPUnit\Event\AbstractEventTestCase` is declared inside a `files`-autoload script — both are real, multi-class-per-file / declared-via-side-effect patterns that pure PSR-4 path derivation (and the `files`-list's deliberate exclusion from the FQCN map) cannot resolve by construction, correctly counted as genuine failures.

Given the existing full test suite after this phase lands, including phase 72's PHP syntactic-axis tests

Then it passes unchanged — this phase only adds new `src/graph/php/*` modules with no call sites wired into `src/engine/model.ts` or `scan()` (that wiring is Phase C per design doc §4), so nothing in the existing scan path changes behavior.

## Tasks

### T1: Composer manifest JSON parser
- files: new `src/graph/php/composer-manifest.ts`
- action: parse a composer.json's `autoload` and `autoload-dev` blocks into typed `psr-4`/`psr-0`/`classmap`/`files` entries (string-dir and array-of-dirs both normalized to `string[]`); missing file, malformed JSON, or missing/empty `autoload`/`autoload-dev` block → empty result, no throw
- verify: unit tests with hand-written composer.json fixtures covering each key shape (single-dir string, array-of-dirs, `autoload-dev` present/absent, missing file, malformed JSON)
- done: AC-1 (manifest-parsing half)

### T2: PSR-4/PSR-0 path-derived map + classmap directory/file scan
- files: new `src/graph/php/composer-autoload.ts`
- action: build the FQCN→file map: `psr-4`/`psr-0` resolved by pure path manipulation against discovered `.php` files (no file reads) per each spec's own convention (§ AC-1) — **longest-prefix-first**, since composer allows overlapping prefixes (e.g. `"App\\": "src/"` alongside `"App\\Models\\": "custom/models/"`) and resolves the longest match; iterating manifest order and taking the first hit silently resolves to the wrong file (mirror `module-resolver.ts`'s own `roots.sort((a,b) => b.length - a.length)` discipline, same failure shape); `classmap` scans candidate dirs/files **filtered from the already-`discoverFiles`-discovered set** (not an independent filesystem walk — keeps `vendor/`'s exclusion, phase 72 T4, as the single source of truth for what's in scope) and uses T3's declared-symbol extractor to read each file's actual namespace + top-level declaration name for the real FQCN; `files` entries collected as a separate unconditionally-included path list, not merged into the FQCN map
- verify: fixture-tree tests — single psr-4 prefix, multiple psr-4 prefixes, array-of-dirs-per-prefix, **two overlapping psr-4 prefixes asserting longest-match wins**, psr-0 with underscore-bearing class name, a psr-0 negative fixture with an underscore in the *namespace* portion asserting it does not itself convert, classmap directory, classmap explicit file list, `files` entries surfaced separately
- done: AC-1

### T3: Namespace + top-level declared-symbol extractor
- files: new `src/graph/php/declared-symbols.ts`
- action: given a parsed PHP file, extract its `namespace_definition` (or `null` for the global namespace) and every top-level `class_declaration`/`interface_declaration`/`trait_declaration`/`enum_declaration` name — all four verified live this session as distinct node types, each with a `name` child — into `{ fqcn, kind, file }` entries; feeds T2's classmap scan
- verify: unit tests on a fixture file containing an interface, a trait, an enum, and a class, asserting all four are extracted with correct FQCNs; a negative case asserting a plain top-level `function_definition` is excluded (composer classmap only autoloads class-like symbols)
- done: AC-1 (classmap correctness)

### T4: Namespace/`use`-import parser
- files: new `src/graph/php/import-parser.ts`
- action: walk `namespace_use_declaration` in every verified shape (§ AC-2: simple `qualified_name`, single-segment bare `name`, aliased via `namespace_aliasing_clause`, grouped via `namespace_use_group`/`namespace_use_group_clause`, `function`/`const`-prefixed via the unnamed keyword-token child) into `{ localName, fqcn, kind }` entries; capture the file's current namespace from `namespace_definition` (or global if absent)
- verify: one unit test per verified `use`-clause shape asserting exact `{ localName, fqcn, kind }` extraction, plus a no-`namespace`-declaration fixture asserting correct global-namespace handling
- done: AC-2

### T5: Reference resolver — PHP name-resolution rules
- files: new `src/graph/php/resolve-import.ts`
- action: given T4's local-binding map, current namespace, and a class-reference name string, implement PHP's actual resolution rules (§ AC-3): leading-backslash → always fully qualified; unqualified single-segment with no matching `use` → current-namespace-qualified, no global fallback; qualified relative name → check first segment against imported aliases, substitute or fall back to current-namespace-relative; resolve the resulting FQCN against T2's autoload map to a file path or `null`
- verify: unit tests for each of the four resolution branches (fully-qualified, unqualified-in-namespace, aliased-qualified-relative, unaliased-qualified-relative), plus unresolvable cases (a PHP built-in class name with no local declaration, a class outside this repo's own autoload map)
- done: AC-3

### T6: End-to-end fixture-tree suite + import-resolution-rate harness
- files: new `test/graph-php-composer-resolver-fixtures.test.ts`, `test/fixtures/php-composer-resolver/**`, new `src/bench/php-import-resolution-rate.ts`, `test/bench-php-import-resolution-rate.test.ts`
- action: fixture-tree suite wires T1–T5 end-to-end (discover → parse composer.json → build autoload map → parse target file's namespace/`use` declarations → resolve each), mirroring `test/graph-python-module-resolver-fixtures.test.ts`'s structure; harness mirrors `src/bench/python-import-resolution-rate.ts`'s `--repo <path>` CLI shape and local-candidate filtering logic (§ AC-4), run manually against local guzzle + phpunit checkouts (not vendored into this repo, not wired into CI), rates recorded in PROGRESS/SUMMARY
- verify: fixture suite green; harness run manually against both checkouts, both ≥95%, numbers recorded in PROGRESS
- done: AC-4, AC-5 (full suite, including this phase's own additions, green)
